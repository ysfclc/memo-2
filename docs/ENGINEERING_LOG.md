**D-013 · 2026-10-26 · Branch-on-failure rescue.** A step that FAILs without a retry policy does NOT immediately fail the run when a LATER BRANCH step explicitly watches that step's FAILED outcome: the engine diverts to that branch (steps between are SKIPPED with "run diverged"); unwatched failures fail the run as before. **D-017 · 2026-10-26 · Async external steps in the workflow engine (M0.A1).** `Attempt.Pending(ticket, pollAfterMs)` lets an executor start work that finishes later (browser tab, app flow, remote job). **D-022 · 2026-10-26 · Encrypted vault: framing, Keystore key and backup rotation (M0.C1).** `app/.../platform/android/vault/VaultFormat.kt` is pure JVM: file framing `MV1 | ivLen(12) | iv | ciphertext||tag`, AES/GCM/NoPadding with a 128-bit tag, AAD `memo:<name>:v1`, IV generated by the provider. `open` validates magic, iv length and truncation before decrypting, and maps every authentication failure to `VaultException`. `backupNames` and `selectReadable` (primary first, then `.bak1..3`) are pure, so the fallback is unit-tested. `app/.../platform/android/vault/KeystoreVault.kt` implements `Vault` over `noBackupFilesDir/vault/`. Key alias `memo_vault_v1`, AES-256, GCM, no padding, randomized encryption required. A key is created only when the vault directory holds no files. If data exists and the key is missing, every operation throws `vault key missing; data cannot be decrypted`, so a new key is never created over existing data (fail closed). Write: seal, write `name.tmp` with `fd.sync()`, rotate backups, then `Files.move(ATOMIC_MOVE, REPLACE_EXISTING)` with a `renameTo` fallback. Rotation copies the current primary to `.bak1` instead of renaming it, so the primary stays present through the whole write. Read falls back to a backup only when the primary is missing or fails to open. The fallback is stored in `lastRecovery` and logged; if nothing opens, read throws and never returns null. `list` hides `.tmp` and `.bak<n>` files, so `write` rejects names with those suffixes; otherwise a write to `x.bak1` would overwrite a backup of `x`. Per-name locks serialise operations on a name; a global lock serialises key creation. All methods do blocking I/O and must run off the main thread. Alternatives considered: a new key on a missing-key read (rejected: silently discards existing data); renaming the primary to `.bak1` (rejected: the primary is absent during the window between the two steps); one ciphertext per file with a random name (rejected: a stable name is what `Vault` callers use). Consequences: a tampered or wrong-key entry is unrecoverable unless a backup opens; `KeystoreVault` is not unit-tested on the JVM (it needs the Keystore), so its verification is CI compilation plus the device checklist (UNVERIFIED on a device). The log numbering skips D-020 and D-021, which are not on this base branch.

**D-021 · 2026-10-26 · Model router, rate limits and provider health (M0.A6).** `core/.../route/` adds `ModelRouter.route(role, targets, prefs, health, limiter, switches, now)`, which returns `Routed(decision)` or `NoRoute(reason)`. `RoutingPreferences` holds one `RoutingMode` per `StepRole` and an optional pinned target id per role; defaults are LOCAL_FIRST for PLAN, CHAT, CAPTURE, DRAFT, SYNTHESIZE and IMAGE, and FRONTIER_FIRST for RESEARCH and CRITIQUE. **D-023 · 2026-10-26 · Gate binding follows the nearest gate; side effects are checkpointed before their executor (M0.F1).** Fixes two lead-review defects in the workflow engine.
- *Binding hole.* The approval a side effect used to bind to was the most recent COMPLETED gate before it. A branch jump or the D-013 failure rescue could skip a later gate, so a side effect after it ran under the older approval (G1 approved, A fails, the rescue skips G2, C runs under G1). Now a side effect binds to the NEAREST preceding HUMAN_APPROVAL step regardless of status. That gate must be COMPLETED, or the engine refuses with HardFail ("nearest preceding gate 'x' is SKIPPED, not COMPLETED"). `deliverExternal` applies the same rule. A vetoed gate is SKIPPED and the veto still skips side effects up to the next gate, as before.
- *Plan-level rule (documented in `WorkflowPolicy.validateSideEffects`): "a branch may not jump over a HUMAN_APPROVAL step".* A BRANCH row is rejected when a gate lies strictly between the branch and its goto target, in either direction. A watched step is rejected when a gate lies strictly between it and its watching branch, because the failure rescue jumps from the watched step to the branch. Gates at the endpoints are allowed. This is a simple range check, not a path analysis. It can reject some safe plans, and it never admits a skipped gate.
- *Crash-safe side effects.* Immediately before a side-effect executor runs, the step is set to RUNNING with ticket `inflight:<idempotencyKey>` and the run is stored and passed to the optional `WorkflowEngine(checkpoint: (AgentRun) -> Unit)` callback. The app persists it synchronously there. If the callback throws, the executor is not invoked and the step fails with "could not checkpoint before side effect". A synchronous result clears the inflight ticket through the normal settlement path (Pending replaces it with the executor's own ticket). `resumeInterrupted` already sends any RUNNING side effect with a ticket to NEEDS_REVIEW, so `inflight:` tickets follow that rule. The new `recoverAfterRestart(runId)` applies the same recovery to a restored RUNNING or INTERRUPTED run and never calls `advance` or any executor. The app calls `advance` itself afterwards when the result is RUNNING. `deliverExternal` refuses an `inflight:` ticket, because that attempt is unconfirmed and must be reviewed.
- Alternatives considered: (a) keep "most recent completed gate" and only fix the planner (rejected: a restored or hand-built run would still bind wrongly); (b) full path analysis of branches (rejected for now: more code and more to review than the range rule needs); (c) checkpoint with a separate state field instead of the ticket (rejected: the ticket field already blocks re-execution and is persisted); (d) let `recoverAfterRestart` call `advance` (rejected: it would run pure executors inside recovery, against the "no executor invoked" rule).
- Consequences: a plan that puts a branch over a gate is now rejected at compile time, so an existing saved plan of that shape must be re-validated (no such saved plans exist yet: the engine has no persistence path in M0). `audit.record` still fires once per completed side effect. The app must wire `checkpoint` to a synchronous store and call `recoverAfterRestart` for each restored RUNNING or INTERRUPTED run; until it does, a crash mid side effect still restores as PENDING. That wiring is outside this task. Verification: `build-memo-apk.yml` runs `:core:test`, which includes `WorkflowEngineSafetyTest` and the existing engine tests; UNVERIFIED until that CI run is green.

### M0 (build plan) · core test repair

First CI run of `:core:test` on `milestone/M0` was red: 6 of 119 tests failed. Each root cause was checked against D-011…D-017 and the KDoc before deciding code or test.

1. **RETRY declarations were rejected as unknown fields (code bug).** `PlanProposalParser` read `attemptsMax` from the RETRY step but did not list it in `KNOWN_STEP_KEYS`, so every declarative retry plan failed with "unknown field(s) attemptsMax". Breaks D-014 and the prompt contract, which advertises `attemptsMax`. Fix: key added. Affected tests: `PlanProposalParserTest.foldsRetryDeclarationsOntoTargets`, `WorkflowEngineTest.retryBackoffWaitsClockAndRecovers`, `WorkflowEngineAsyncTest.deliveredFailureFollowsRetryPolicy` (the NPEs were the `plan()` helper's `spec!!`).
2. **Branch-on-failure rescue never ran for hard failures (code bug).** `WorkflowEngine.advance` returned on `StepOutcome.HardFail` before the top-of-loop `FAILED` branch could look for a watching branch step, so D-013 rescue only worked for steps whose state was already FAILED. Fix: `HardFail` now loops back to the FAILED path, which either diverts (rescue) or fails the run as before. Fail-fast is preserved for unwatched failures. Affected test: `WorkflowEngineTest.branchOnFailureDivertsToFallbackPath`.
3. **Host matching was case-sensitive on the provider id (code gap).** `hostBelongsTo` lowercased host names but looked up the provider id as given, so `hostBelongsTo("Grok", "WWW.grok.com")` returned false. The parser's provider whitelist stays exact-match and lowercase; only the domain-family check now normalises the id. Affected test: `CatalogTest.hostMatchingIsDomainFamilyAware`.
4. **Frontier prompt test expected a thousands separator the prompt never emits (test error).** `Prompts.frontierSystem` surfaces the output cap as a plain integer (`1234`), the same as `frontierUserEnvelope` (asserted as `999` in `envelopeCarriesBriefPacketAndCap`). The test comment says "surfaced verbatim". The assertion was changed from `"1,234"` to `"1234"`; the honesty and injection framing assertions are unchanged. Affected test: `PromptContractTest.frontierPromptsCarryHonestyAndInjectionFraming`.
