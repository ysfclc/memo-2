**D-013 · 2026-10-26 · Branch-on-failure rescue.** A step that FAILs without a retry policy does NOT immediately fail the run when a LATER BRANCH step explicitly watches that step's FAILED outcome: the engine diverts to that branch (steps between are SKIPPED with "run diverged"); unwatched failures fail the run as before. **D-022 · 2026-10-26 · Encrypted vault: framing, Keystore key and backup rotation (M0.C1).** `app/.../platform/android/vault/VaultFormat.kt` is pure JVM: file framing `MV1 | ivLen(12) | iv | ciphertext||tag`, AES/GCM/NoPadding with a 128-bit tag, AAD `memo:<name>:v1`, IV generated by the provider. `open` validates magic, iv length and truncation before decrypting, and maps every authentication failure to `VaultException`. `backupNames` and `selectReadable` (primary first, then `.bak1..3`) are pure, so the fallback is unit-tested. `app/.../platform/android/vault/KeystoreVault.kt` implements `Vault` over `noBackupFilesDir/vault/`. Key alias `memo_vault_v1`, AES-256, GCM, no padding, randomized encryption required. A key is created only when the vault directory holds no files. If data exists and the key is missing, every operation throws `vault key missing; data cannot be decrypted`, so a new key is never created over existing data (fail closed). Write: seal, write `name.tmp` with `fd.sync()`, rotate backups, then `Files.move(ATOMIC_MOVE, REPLACE_EXISTING)` with a `renameTo` fallback. Rotation copies the current primary to `.bak1` instead of renaming it, so the primary stays present through the whole write. Read falls back to a backup only when the primary is missing or fails to open. The fallback is stored in `lastRecovery` and logged; if nothing opens, read throws and never returns null. `list` hides `.tmp` and `.bak<n>` files, so `write` rejects names with those suffixes; otherwise a write to `x.bak1` would overwrite a backup of `x`. Per-name locks serialise operations on a name; a global lock serialises key creation. All methods do blocking I/O and must run off the main thread. Alternatives considered: a new key on a missing-key read (rejected: silently discards existing data); renaming the primary to `.bak1` (rejected: the primary is absent during the window between the two steps); one ciphertext per file with a random name (rejected: a stable name is what `Vault` callers use). Consequences: a tampered or wrong-key entry is unrecoverable unless a backup opens; `KeystoreVault` is not unit-tested on the JVM (it needs the Keystore), so its verification is CI compilation plus the device checklist (UNVERIFIED on a device). **D-023 · 2026-10-26 · Gate binding follows the nearest gate; side effects are checkpointed before their executor (M0.F1).** Fixes two lead-review defects in the workflow engine.
- *Binding hole.* The approval a side effect used to bind to was the most recent COMPLETED gate before it. A branch jump or the D-013 failure rescue could skip a later gate, so a side effect after it ran under the older approval (G1 approved, A fails, the rescue skips G2, C runs under G1). Now a side effect binds to the NEAREST preceding HUMAN_APPROVAL step regardless of status. That gate must be COMPLETED, or the engine refuses with HardFail ("nearest preceding gate 'x' is SKIPPED, not COMPLETED"). `deliverExternal` applies the same rule. A vetoed gate is SKIPPED and the veto still skips side effects up to the next gate, as before.
- *Plan-level rule (documented in `WorkflowPolicy.validateSideEffects`): "a branch may not jump over a HUMAN_APPROVAL step".* A BRANCH row is rejected when a gate lies strictly between the branch and its goto target, in either direction. A watched step is rejected when a gate lies strictly between it and its watching branch, because the failure rescue jumps from the watched step to the branch. Gates at the endpoints are allowed. This is a simple range check, not a path analysis. It can reject some safe plans, and it never admits a skipped gate.
- *Crash-safe side effects.* Immediately before a side-effect executor runs, the step is set to RUNNING with ticket `inflight:<idempotencyKey>` and the run is stored and passed to the optional `WorkflowEngine(checkpoint: (AgentRun) -> Unit)` callback. The app persists it synchronously there. If the callback throws, the executor is not invoked and the step fails with "could not checkpoint before side effect". A synchronous result clears the inflight ticket through the normal settlement path (Pending replaces it with the executor's own ticket). `resumeInterrupted` already sends any RUNNING side effect with a ticket to NEEDS_REVIEW, so `inflight:` tickets follow that rule. The new `recoverAfterRestart(runId)` applies the same recovery to a restored RUNNING or INTERRUPTED run and never calls `advance` or any executor. The app calls `advance` itself afterwards when the result is RUNNING. `deliverExternal` refuses an `inflight:` ticket, because that attempt is unconfirmed and must be reviewed.
- Alternatives considered: (a) keep "most recent completed gate" and only fix the planner (rejected: a restored or hand-built run would still bind wrongly); (b) full path analysis of branches (rejected for now: more code and more to review than the range rule needs); (c) checkpoint with a separate state field instead of the ticket (rejected: the ticket field already blocks re-execution and is persisted); (d) let `recoverAfterRestart` call `advance` (rejected: it would run pure executors inside recovery, against the "no executor invoked" rule).
- Consequences: a plan that puts a branch over a gate is now rejected at compile time, so an existing saved plan of that shape must be re-validated (no such saved plans exist yet: the engine has no persistence path in M0). `audit.record` still fires once per completed side effect. The app must wire `checkpoint` to a synchronous store and call `recoverAfterRestart` for each restored RUNNING or INTERRUPTED run; until it does, a crash mid side effect still restores as PENDING. That wiring is outside this task. Verification: `build-memo-apk.yml` runs `:core:test`, which includes `WorkflowEngineSafetyTest` and the existing engine tests; UNVERIFIED until that CI run is green.

### M1 · CHAT (wp/chat) · M1.C1 conversation store

- **Decision · one vault entry per conversation.** Entry `chat_<id>` holds the conversation and its messages (`ConversationDoc`, format v1, strict parse with exact field sets and enum names). Entry `chat_index` holds metadata only, so the list does not decrypt every conversation. Conversation ids are 32 lowercase hex characters from `SecureRandom`, which makes `chat_<id>` a valid `VaultName`. Alternatives: one entry for all chats (rejected: one corrupt write would put every conversation at risk, and the size is unbounded); messages as separate entries (rejected: many small writes and no atomic doc).
- **Corruption rule.** A conversation entry that fails to read or decode is blocked and reported; saves for that id are refused and the stored bytes are never changed. Deleting it stays available as an explicit action. A corrupt index is kept on disk and the list is rebuilt from entries, but the index is not written again until a later load reads it cleanly. An indexed conversation is listed without decrypting it, so its corruption shows when it is opened, not at load (UNVERIFIED on device).
- **Writes.** `ChatRepository` writes on one background thread, in order. Reads go through the same thread so they see queued writes.
- **Titles.** Derived once from the first user message, at most 48 characters, cut at a word boundary, never inside a surrogate pair.
- **Search.** Folds Turkish dotted and dotless i to `i` and Polish stroked l to `l` before NFD and mark removal. A blank query matches everything.
